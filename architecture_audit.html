問題痛點：外部呼叫端（如 routers/student.py）被迫理解 Supabase 與本地 JSON 的欄位差異，手動由 raw 提取 current_cycle_lesson，導致昨晚的 7/8 堂顯示脫節 Bug。

重構解法：將 data_gateway.py 升級為強型別 Repository，介面僅暴露純粹的 Student 物件，內部完全消化雲端/本地多資料來源與 Fallback 策略。

架構收益 (Wins)：
  • Locality：資料合併與解包 Bug 集中單一模組。
  • Interface shrinks：路由層不再出現任何 raw 取值邏輯。
  • Leverage：Web 路由、定時排程、測試共用相同穩定實體。

問題痛點：teaching_sync.py 既要負責文字教案解析與學員關聯，又要呼叫 Heptabase CLI 導圖與處理 PIL 二進位圖檔壓制，責任邊界嚴重模糊。

重構解法：將圖片提取、格式校正、壓制與 Git 遠端推送閉環封裝進獨立的 ImageSyncEngine 深模組，讓 teaching_sync.py 專注於教學資料結構。

架構收益 (Wins)：
  • Seam：圖檔處理與文字解析完全解耦。
  • Testability：圖片自癒可獨立進行離線 Mock 測試。
  • Delete wrappers：消除多處重複定義的檔案比對與路徑解析代碼。

3. 建立 StudentProfileAssembler：收斂視圖模型聚合邏輯

Worth Exploring view-model aggregator
檔案路徑: routers/student.py (322行) · student_timeline_service.py · digital_management_service.py

問題痛點：routers/student.py 的 read_student 端點包含過多程序性代碼：合體 cloud_meta 與 file_meta、呼叫 predict_student_status、產生 briefing、產生 renewal_message。

重構解法：引入 StudentProfileAssembler 深模組，路由端點只需傳入 student_id，直接取得完全組裝好的視圖模型，路由代碼降至 10 行以內。

架構收益 (Wins)：
  • Locality：視圖組裝規則不洩漏於 HTTP 控制層。
  • Leverage：Web 介面與未來 NativeApp / 桌面客戶端可共享相同視圖聚合器。
